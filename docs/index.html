Marco teorico obligatorio

Lectura del codigo desde A Philosophy of Software Design

La evaluacion usa la terminologia de John Ousterhout: Complexity, Deep Modules, Shallow Modules, Information Hiding, Information Leakage y Change Amplification.

Complexity

La complejidad aparece cuando el cambio exige demasiada carga mental: entender estados, proveedores, permisos, efectos de red y dependencias cruzadas antes de hacer una modificacion simple.

Deep Modules

Un modulo profundo ofrece una interfaz pequena y esconde una implementacion grande. En este proyecto, los mejores ejemplos viven en servicios de dominio y en el cliente HTTP del frontend.

Shallow Modules

Un modulo superficial obliga a pagar mucho costo de interfaz por poca implementacion. El riesgo aparecio cuando endpoints, componentes y proveedores intentaron crecer como piezas aisladas.

Information Leakage

Hay fuga de informacion cuando una decision interna se filtra a otra capa. La auditoria revisa si la UI conoce detalles de SQL, Cloudinary, Meta Cloud API, Wompi o firmas de integridad.

Seccion 1

La Bala Trazadora y el enrutamiento de las skills

La skill .claude/skills/grill-me forzo al equipo a recorrer el arbol de decisiones antes de escribir codigo: comprador sin cuenta, administrador autenticado, token publico opaco, estados de numero calculados y proveedores externos con modo sandbox.

Esa entrevista cambio la suposicion inicial de "hacer pantallas" por una estrategia de arquitectura: primero probar el tramo mas incierto del sistema, donde una seleccion visual se convertia en reserva, pago, estado de numero y feedback al usuario.

Tracer Bullet elegido

El issue de integracion mas riesgoso fue la cadena GET /r/{public_token} -> grilla -> reserva -> checkout/efectivo -> webhook o confirmacion manual.

  • backend/app/services/raffles.py centraliza reserva, expiracion y confirmacion.
  • backend/app/services/wompi.py concentra referencia, firma y webhook.
  • frontend/src/pages/PublicRaffle.jsx consume estados simples: available, reserved, sold.
  • backend/tests/test_006_reserva_numeros.py y test_007_pago_wompi.py validan el tramo temprano.

Fuga evitada: base de datos

La UI no consulta tablas ni estados SQLModel. Recibe DTOs con conteos y estados de dominio. La regla "sold = reserva pagada" vive en get_number_states, no en React.

Fuga evitada: proveedores externos

Cloudinary y Meta Cloud API quedan detras de servicios. En local, el sandbox registra intenciones y evita que una credencial ausente bloquee la confirmacion de un pago.

Residuo aceptado

Los estados pending, paid y expired llegan al dashboard porque son lenguaje del dominio. No se consideran fuga mientras no arrastren detalles de tablas, proveedores o transacciones internas.

Seccion 3

Veredicto retrospectivo de los sub-agentes

El archivo architecture-checkpoint.md registra tres propuestas: extender el servicio de aplicacion, crear puertos por integracion o resolverlo directo en endpoints. La solucion final fue hibrida: servicio de aplicacion para el flujo transaccional y puerto simple para WhatsApp.

En retrospectiva, esa eleccion acelero la segunda mitad: agregar imagen de premio y notificacion no obligo a reescribir rutas publicas ni componentes de comprador. El sistema gano elasticidad porque las integraciones quedaron como decisiones ocultas.

Buen gusto arquitectonico

El mejor gusto del proyecto esta en mantener reglas de negocio cerca del dominio y proveedores externos lejos de la UI. El punto fragil es la pantalla de administracion: aun cumple, pero su tamano anuncia futuras modificaciones consecuentes si se agregan ganador, recordatorios y metricas avanzadas.
